# review-domain

## 目的

`doc/models/`、`src/Domain`、`test/Domain` を照合し、Domain 層の正確性・完全性・保守性をレビューする。原則としてレビュー中にコードを変更しない。

## 手順

1. `CLAUDE.md` と対象 Markdown / PlantUML / mermaid を読む。
2. 対象の Domain 実装・テスト、および関連する共通モデルを読む。
3. ドキュメントの各要素をコード・テストに対応づける。
4. 以下の観点で問題を特定する。
5. 必要な範囲でテスト、型チェック、Lintを実行し、実行結果を確認する。
6. 指摘を重大度順に報告する。

## レビュー観点

### 仕様適合性
- エンティティ、値オブジェクト、集約、識別子、関連、多重度が定義と一致しているか
- 不変条件、状態遷移、業務ルールが漏れなく実装されているか
- ドキュメントにない仕様を追加していないか
- Markdown と PlantUML / mermaid の矛盾を見落としていないか

### DDD
- 集約境界とトランザクション整合性の考え方が妥当か
- 集約ルートが不変条件を保護しているか
- エンティティと値オブジェクトの区別が適切か
- ドメインサービスに置くべき処理とモデル自身の振る舞いが適切に分かれているか
- ドメインイベントが事実を表し、発行条件が明確か

### TypeScript / 品質
- 型が業務概念を正しく表現しているか
- 不正な状態を生成できない設計か
- 不必要な `any`、型アサーション、可変状態がないか
- 例外・エラー型が適切か
- 技術ライブラリへの不要な依存がないか

### テスト
- 正常系、異常系、境界値、不変条件、状態遷移を網羅しているか
- テストが実装詳細ではなく振る舞いを検証しているか
- 重要な仕様に対してテストが欠落していないか
- テストが不適切に skip / only されていないか

### アーキテクチャ
- Domain が Application / Infrastructure / Presentation に依存していないか
- DB、Express、DIコンテナ等の技術詳細が侵入していないか

## 指摘の形式

各指摘に次を含める。

- ID（例：DOM-001）
- 重大度：Critical / High / Medium / Low
- 対象ファイル・行番号
- 根拠となるドキュメント箇所
- 問題と発生し得る影響
- 修正方針（具体案）
- 必要なテスト

重大度の目安：
- Critical：不変条件破壊、データ整合性・セキュリティに重大な問題
- High：主要な業務ルールの欠落・誤実装、集約境界の重大な誤り
- Medium：保守性・拡張性・例外処理・テストの重要な不足
- Low：命名、軽微な重複、改善提案

## 禁止事項

- 指摘を黙って修正しない。
- ドキュメントの曖昧さを実装不備と断定しない。仕様確認事項として分離する。
- 根拠のない好みを欠陥として扱わない。

## 報告

総合判定（Pass / Pass with concerns / Needs changes）、指摘一覧、仕様確認事項、テスト等の実行結果、次工程へのブロッカーを報告する。Critical / High が残る場合は次工程に進まないよう明記する。
