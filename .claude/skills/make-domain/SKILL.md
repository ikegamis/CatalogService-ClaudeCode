# make-domain

## 目的

人間が定義したドメインモデルを読み取り、対象範囲の Domain 層コードと Domain 単体テストを作成する。

## 入力・対象範囲

- 引数で対象機能・集約・ドキュメントが指定された場合は、その範囲を対象とする。
- 指定がない場合は、`doc/models/` を調査し、実装可能なモデルを特定する。ただし、複数の独立した集約・機能を一度に実装せず、対象候補を提示して確認する。
- 参照する共通用語集、コンテキストマップ、関連集約の定義も読む。

## 手順

1. `CLAUDE.md` と対象の Markdown / PlantUML を読む。
2. 既存の `src/Domain` と `test/Domain`、`package.json`、TypeScript/Jest設定を確認する。
3. 実装前に次のモデル要素を整理する。
   - 集約、集約ルート、境界
   - エンティティと識別子
   - 値オブジェクトと生成時検証
   - 不変条件、状態遷移、振る舞い
     - リポジトリに対する振る舞いがあったら Interface としてオブジェクトとは別に定義する
   - ドメインサービス、ドメインイベント
   - 他集約との参照関係
4. ドキュメントの矛盾・不足・曖昧さを検出する。実装の正しさに影響する未確定事項があれば、コードを作らず質問する。軽微な命名上の不明点は既存規約に合わせ、判断を報告する。
5. `src/Domain/Models`、`Services`、`Shared` に適切なサブフォルダを作成して実装する。
6. `test/Domain` にモデルと対応するテストを作成する。
7. テストを実行する。必要に応じて型チェックとLintも実行する。
8. 実装とテストがドキュメントの各ルールをカバーしているか確認する。

## 実装ルール

- 業務上の不変条件は Domain に置き、コンストラクター／ファクトリ／メソッドで守る。
- 集約ルートを介さずに内部エンティティを変更できる公開APIを作らない。
- 値オブジェクトは不変とし、値としての等価性を実装する。
- 識別子型を適切に定義し、異なる識別子の混同を防ぐ。
- ドメインモデルを `tsyringe`、Express、PostgreSQL、外部ライブラリに依存させない。
- Repository の抽象を追加する必要がある場合は、既存方針と `CLAUDE.md` に従う。永続化実装は作らない。
- ドメインイベントは仕様に明記された事実のみ実装する。
- 仕様にない getter、setter、状態、バリデーション、イベントを推測で追加しない。
- `any`、型アサーションによる強引な回避、無意味な抽象化を避ける。

## テスト要件

- 正常系、境界値、異常系、不変条件違反、状態遷移をテストする。
- 値オブジェクトの等価性・不正値拒否をテストする。
- 集約ルート経由でのみ正しい状態遷移が行われることをテストする。
- ドキュメントの各不変条件に対応するテストがあるか確認する。
- テスト名は業務上の振る舞いが分かる表現にする。
- テストを通すために本番コードの制約を弱めない。

## 完了条件

- 対象ドキュメントのモデル要素が Domain コードに反映されている。
- 重要な不変条件・振る舞いにテストがある。
- Domain が外側の層や技術詳細に依存していない。
- 対象テストを実行し、結果を確認している。

## 報告

作成ファイル、モデル対応表、不変条件とテストの対応、実行コマンドと結果、未確定事項、次工程への注意点を報告する。
