# make-application

## 目的

対象ユースケースを実現する Application 層のアプリケーションサービス、入出力モデル、必要なポートとテストを作成する。

## 手順

1. `CLAUDE.md`、対象の `doc/models/`、関連するユースケース記述を読む。
2. `src/Domain` と `test/Domain` の実装・テストを確認する。Domain の仕様とコードに不一致があれば、先に報告して停止する。
3. 既存の Application 実装、テスト、設定を確認する。
4. ユースケースごとに次を整理する。
   - 呼び出し元と入力
   - 事前条件・認可上の前提（認可判定の責務をどこに置くか）
   - 処理手順と Domain の呼び出し
   - Repository 等の必要なポート
   - トランザクション境界
     - トランザクションについては`./transaction.md`も参照する
   - 出力・業務エラー
   - ドメインイベント／Outbox等の要否
5. 不明点・仕様矛盾が処理結果や整合性に影響する場合は実装前に質問する。
6. `src/Application/Services`、`EventStore`、`Shared` に実装する。
7. `test/Application` にテストを作成する。
8. テスト、型チェック、Lintを実行する。

## 実装ルール

- アプリケーションサービスはユースケースのオーケストレーションに専念する。
- 業務上の判断・不変条件を Application に重複実装せず Domain に委譲する。
- Application は Domain に依存するが、Infrastructure / Presentation に依存しない。
- Repository、Unit of Work、EventStore、外部通知等が必要な場合はポートとして定義する。具象実装は作らない。
- ポートの配置は既存方針に従う。Domain の集約永続化ポートは Domain、ユースケース固有の外部連携ポートは Application を基本候補とする。
- Application の DTO と Domain オブジェクトを分離する。Domain オブジェクトをそのまま外部公開用 DTO にしない。
- `tsyringe`、Express、SQLドライバーを Application に依存させない。
- 読み取りユースケースと更新ユースケースを必要に応じて分離するが、CQRSを形式的に導入しない。
- トランザクションはユースケースの整合性要件に基づいて境界を定義する。
- EventStore を利用する場合、イベントの追記・取得、バージョン競合、イベントスキーマを明示する。
- 仕様にないリトライ、冪等性、補償処理を追加せず、必要性があれば確認事項として報告する。

## テスト要件

- Repository 等のポートはテストダブルで置き換える。
- 正常系、対象なし、業務エラー、ポート障害、境界値をテストする。
- Domain の振る舞いを過剰にモックせず、Domain の実モデルを利用する。
- 呼び出し順序や保存・通知の結果は、ユースケースの契約として必要な範囲で検証する。
- トランザクションの開始・コミット・ロールバック要件をテストする。
- 外部I/OやDBの実動作は Infrastructure テストで検証し、Application テストに混在させない。

## 完了条件

- ドキュメントに定義された対象ユースケースが実装されている。
- Application が内側の Domain とポートだけに依存している。
- 主要なユースケース分岐とエラーをテストしている。
- 対象テスト・型チェック・Lintの結果を確認している。

## 報告

ユースケース一覧、作成ファイル、ポートと依存関係、トランザクション方針、テスト結果、未確定事項を報告する。
