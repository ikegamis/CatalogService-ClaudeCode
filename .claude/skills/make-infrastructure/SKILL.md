# make-infrastructure

## 目的

Domain / Application が定義したポートを実装し、InMemory および PostgreSQL 17 の永続化アダプターとテストを作成する。

## 手順

1. `CLAUDE.md`、対象ドキュメント、Domain / Application のコードとテストを読む。
2. ポート（Repository、Unit of Work、EventStore、Outbox等）と契約を一覧化する。
3. 既存のSQL接続、マイグレーション、設定、ログ、DI登録、テスト環境を確認する。
4. テーブル・制約・インデックス・トランザクション・ロック・マッピング方針を整理する。
5. DBスキーマやマイグレーションが未定義で、データ構造に影響する場合は確認する。ドキュメントから導ける範囲と推測を明確に分ける。
6. `src/Infrastructure/InMemory` と `src/Infrastructure/SQL` にポート実装を作成する。
7. 必要なマイグレーションを既存方針に従って作成する。既存DBへの適用はユーザーの明示的な承認なしに実行しない。
8. `test/Infrastructure` に契約テスト・統合テストを作成する。
9. テスト、型チェック、Lintを実行する。

## 実装ルール

- Infrastructure は Domain / Application のポートを実装する。内側の層にInfrastructureの型を漏らさない。
- Repository は集約の読み書きを担当し、集約ルート経由で不変条件を守る。
- SQLの値は必ずパラメーター化する。
- DB制約を活用し、競合・一意制約違反・外部キー違反を適切なエラーに変換する。
- 接続プール、接続解放、タイムアウト、トランザクション終了処理を適切に実装する。
- 複数SQL文の原子性が必要な処理では同一トランザクションを利用する。
- SQL実装と InMemory 実装は同じポート契約を満たす。
- InMemory 実装を本番永続化として扱わない。
- DBの日時・数値・JSON等の型変換を明示し、精度やタイムゾーンを損なわない。
- マイグレーションは前進・ロールバック方針、既存データへの影響を明記する。
- EventStore を実装する場合、追記専用性、ストリーム識別子、バージョン競合、イベントスキーマ、再構成を検証する。
- Outbox を実装する場合、業務データ更新との同一トランザクション、未送信抽出、ロック、再試行、重複配信への対処を明確にする。
- CQRS の Read Model は更新モデルと別の要件がある場合に限って実装する。
- 接続文字列や秘密情報をコードにハードコードしない。
- 対象がSQLの場合、スキーマ定義を行う `src/Inrastructure/SQL/schema.sql' を作成すること。
- 対象がSQLの場合でマイグレーションがある場合、マイグレーションを行うための スクリプト `src/Inrastructure/SQL/migrations.ts' を作成すること

## テスト要件

- InMemory と SQL の両方でポート契約を検証する。
- SQL統合テストは PostgreSQL 17 を使用し、可能ならテストごとに独立したデータ状態を確保する。
- 保存・取得・更新・削除（仕様に存在する場合）、一意制約、同時更新、ロールバックを検証する。
- 集約の再構成後も不変条件・値が保たれることを検証する。
- SQLテストを実行できない場合は、未実施理由と必要な環境を明記する。InMemoryテストをSQL統合テストの代わりと報告しない。
- 外部イベント連携では重複、再試行、失敗途中の状態を検証する。

## 完了条件

- 対象ポートの必要な実装がそろっている。
- SQL実装がPostgreSQL 17で検証されている、または未実施理由が明確である。
- InMemory / SQL がポート契約を満たしている。
- トランザクション・制約・エラー変換がテストされている。

## 報告

実装したポート、テーブル・マイグレーション、トランザクション方針、テスト環境・コマンド・結果、未実施テスト、運用上の注意点を報告する。
